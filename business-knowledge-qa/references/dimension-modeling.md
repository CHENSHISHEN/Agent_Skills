# 维度建模方法论 (Kimball)

## 核心概念

### 维度建模的四步流程

#### 第一步：选择业务过程
- **定义**: 业务过程中组织中发生的业务活动或操作，通常由某个事件触发
- **特点**:
  - 有明确的时间点
  - 产生度量数据
  - 业务可理解
- **示例**:
  - 企业注册、变更、注销
  - 投融资事件
  - 专利申请、授权
  - 司法案件立案

#### 第二步：声明粒度
- **定义**: 事实表中一行数据代表的业务含义
- **重要性**: 粒度决定了维度的关联方式和度量的聚合层次
- **示例**:
  - 投融资事件：每次投资活动
  - 专利引用：每对专利的引用关系
  - 日志数据：每次用户点击
- **原子粒度原则**: 尽可能选择最细粒度，以支持灵活的上卷

#### 第三步：确定维度
- **5W1H分析法**:
  - **Who**: 谁（参与主体）→ 企业、人才、机构
  - **What**: 什么（业务对象）→ 专利、项目、资金
  - **When**: 何时（时间维度）→ 日期、月份、年份
  - **Where**: 何地（地点维度）→ 省份、城市、区县
  - **Why**: 为什么（原因维度）→ 投资轮次、案件类型
  - **How**: 如何（方式维度）→ 支付方式、申请渠道

#### 第四步：确定事实
- **事实类型**:
  - **可加性事实**: 可跨所有维度聚合（金额、数量）
  - **半可加性事实**: 只能沿部分维度聚合（库存、余额）
  - **不可加性事实**: 不可聚合（比率、百分比）

## 维度表设计

### 维度类型

#### 1. 实体维度 (Entity Dimension)
- 描述独立存在的业务对象
- **示例**: 企业、人才、专利、项目
- **特点**:
  - 有生命周期（创建、变更、消亡）
  - 跨业务过程共享
  - 包含丰富的描述性属性

#### 2. 角色扮演维度 (Role-Playing Dimension)
- 同一物理维度在不同场景下的不同角色
- **示例**:
  - 日期维度作为"申请日期"、"授权日期"、"公告日期"
  - 企业维度作为"投资方"、"被投方"
- **处理方式**: 使用视图或别名

#### 3. 退化维度 (Degenerate Dimension)
- 维度属性过于简单，不值得单独建表
- **示例**:
  - 订单号
  - 案件编号
  - 交易流水号
- **处理方式**: 直接存储在事实表中

#### 4. 缓慢变化维度 (Slowly Changing Dimensions)

**SCD Type 1**: 覆盖更新
- **适用**: 历史不重要，只看最新状态
- **示例**: 企业联系电话、企业邮箱
- **实现**: 直接UPDATE

**SCD Type 2**: 保留历史
- **适用**: 需要追踪历史变化
- **示例**: 企业经营范围、股权结构
- **实现**:
  - 增加字段: `scd_start_date`, `scd_end_date`, `is_current`
  - 插入新记录而非UPDATE

**SCD Type 3**: 折中方案
- **适用**: 只保留当前和上一个状态
- **实现**: 增加`previous_value`字段
- **本项目中**: 推荐使用Type 1或Type 2

#### 5. 多值维度 (Multi-Valued Dimension)
- 一个事实关联多个维度值
- **示例**:
  - 一个专利有多个申请人
  - 一个项目有多个研究机构
- **处理方式**: 使用桥接表

#### 6. 层次维度 (Hierarchical Dimension)
- 维度属性存在层级关系
- **示例**:
  - 地理位置: 国家 > 省 > 市 > 区县
  - 行业分类: 门类 > 大类 > 中类 > 小类
  - 教育层次: 学科门类 > 一级学科 > 二级学科
- **处理方式**: 扁平化存储（level_1, level_2, level_3）

## 事实表设计

### 事实表类型

#### 1. 事务事实表 (Transaction Fact Table)
- **定义**: 记录业务过程中的原子事件
- **特点**:
  - 每行对应一次业务事件
  - 事件发生时立即加载
  - 不可修改
- **示例**:
  - 投融资事件
  - 专利申请事件
  - 工商变更事件

#### 2. 周期快照事实表 (Periodic Snapshot Fact Table)
- **定义**: 按固定时间间隔记录状态
- **特点**:
  - 定期加载（每天/每月）
  - 包含截至当时的累积度量
  - 便于趋势分析
- **示例**:
  - 每日账户余额
  - 每月库存快照
  - 每日企业案件统计

#### 3. 累积快照事实表 (Accumulating Snapshot Fact Table)
- **定义**: 记录有明确开始和结束的业务过程
- **特点**:
  - 包含多个日期字段（开始、里程碑、结束）
  - 随过程推进不断更新
- **示例**:
  - 项目全流程（立项→实施→验收）
  - 专利审批（申请→公开→实审→授权）
  - 企业上市（辅导→受理→过会→挂牌）

### 事实表设计原则

1. **保持粒度一致**:
   - 所有度量必须是同一粒度
   - 不能混杂不同粒度的度量

2. **分离不同粒度**:
   - 不同粒度的事实放在不同表中
   - 示例: 每日订单 vs 每月订单

3. **避免过度汇总**:
   - 优先原子粒度
   - 支持灵活的上卷聚合

4. **处理NULL值**:
   - 数值度量: NULL表示不存在（区别于0）
   - 外键: NULL表示无关联

## 维度关系处理

### 1:1 关系
- **处理**: 合并到同一个维度表
- **示例**: 企业基础信息 + 企业工商信息

### N:1 关系
- **处理**: 在事实表中添加外键
- **示例**: 多个投融资事件 → 一个企业

### N:M 关系（多对多）
- **处理**: 创建桥接表
- **示例**: 企业 ↔ 人才（股东、高管）
- **桥接表字段**:
  - `pk_bridge_id`: 主键
  - `sk_enterprise_id`: 企业外键
  - `sk_talent_id`: 人才外键
  - `role_type`: 角色类型（董事长、CEO等）

### 递归关系（自关联）
- **示例**: 企业股权穿透（母公司→子公司→孙公司）
- **处理**: 使用层次维度或递归CTE
- **本项目**: 不推荐递归，使用层次字段扁平化

## 设计反模式

### ❌ 避免的做法

1. **直接维度到维度JOIN**:
   ```
   ❌ SELECT * FROM dim_enterprise e JOIN dim_talent t ON e.leader_id = t.id
   ✅ 使用桥接表: bridge_enterprise_talent_relation
   ```

2. **大文本字段放入事实表**:
   ```
   ❌ 事实表包含 patent_abstract (可能几千字)
   ✅ 使用支撑表: og_patent_text
   ```

3. **度量跨不同粒度**:
   ```
   ❌ 同一表包含: 每日营收 + 每月营收
   ✅ 分表: fact_revenue_daily + fact_revenue_monthly
   ```

4. **枚举值不建立维度**:
   ```
   ❌ 直接存储 '01', '02', '03'
   ✅ 关联枚举维度表或使用退化维度+字典
   ```

5. **缺少唯一主键**:
   ```
   ❌ 事实表主键不唯一导致重复计数
   ✅ 使用pk_*确保唯一性
   ```

## 实战检查清单

设计新表时，检查：

### 业务理解
- [ ] 明确的业务过程是什么？
- [ ] 这个表解决什么业务问题？
- [ ] 谁会使用这个表？

### 粒度声明
- [ ] 能否用一句话描述"一行代表什么"？
- [ ] 粒度是否为原子粒度？
- [ ] 所有度量是否都是同一粒度？

### 维度设计
- [ ] 所有5W1H维度都识别了吗？
- [ ] N:M关系是否使用桥接表？
- [ ] 大文本字段是否分离到支撑表？
- [ ] 层次维度是否扁平化？

### 事实设计
- [ ] 事实类型明确（事务/快照/累积）？
- [ ] 度量的可加性分析清楚？
- [ ] NULL值含义明确？

### 技术规范
- [ ] 主键使用正确的前缀（pk_/bk_）？
- [ ] 代理键使用xxhash64生成？
- [ ] 外键失败时标记为-1？
- [ ] 所有字段都有中文注释？
- [ ] 包含全量分区？
