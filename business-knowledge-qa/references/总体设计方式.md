# DWT要素主题库维度建模设计方法论

## 一、设计理念与原则

### 1.1 核心设计理念
DWT层作为数据仓库的要素主题库，采用**维度建模**方法论，构建面向分析的星型/雪花型模型。设计过程遵循"业务驱动、规范引领、迭代优化"的原则，确保模型既满足业务需求，又具备良好的扩展性和性能。

### 1.2 设计原则
- **业务导向**：深入理解业务过程，准确识别业务事件和度量指标
- **规范统一**：严格遵循命名规范、数据类型标准和建模规范
- **性能优先**：合理设计分区策略、索引结构，确保查询性能
- **扩展灵活**：预留扩展点，支持业务演进和新需求接入

## 二、维度建模设计流程

### 2.1 业务理解与需求分析

#### 第一步：识别核心业务过程
以实际主题域为例，梳理核心业务过程：

| 主题域 | 核心业务过程 | 关键业务事件 |
|--------|------------|------------|
| **材料主题** | 研报发布与使用 | 研报发布、图表引用、作者署名 |
| **专利主题** | 专利全生命周期管理 | 专利申请、授权、交易、法律状态变更 |
| **政策主题** | 政策发布与扶持 | 政策发布、资金扶持分配 |
| **标签主题** | 实体分类与标注 | 产业链定位、标签打标 |
| **投融资主题** | 投融资交易 | 投资事件、退出事件、机构参与 |

#### 第二步：明确分析需求
针对每个业务过程，明确具体的分析需求：
- **度量什么**（What）：确定关键度量指标
- **按什么维度**（How）：识别分析维度
- **粒度要求**（Grain）：定义数据粒度

### 2.2 概念模型设计

#### 第一步：实体识别与分类
基于业务理解，识别并分类核心实体：

```
实体类型划分：
├── 事实型实体（记录业务事件）
│   ├── 交易类：投融资事件、专利交易、政策扶持
│   ├── 快照类：专利生命周期快照、研报记录
│   └── 累积类：价值评估、法律状态变更
├── 维度型实体（描述性属性）
│   ├── 主体维度：企业、机构、研究员、关系方
│   ├── 对象维度：专利、研报、政策、基金
│   └── 分类维度：产业链、标签体系、融资轮次
└── 关系型实体（多对多关系）
    ├── 桥接表：研报-作者、专利-分类、基金-管理人
    └── 支架表：多语种文本、扩展属性
```

#### 第二步：关系梳理
明确实体间的关系类型和基数：
- **1:1关系**：事实表与其详情维度表（如投资事件与投资事件详情）
- **N:1关系**：事实表与共享维度表（如多个事件共享日期维度）
- **N:M关系**：通过桥接表解耦（如研报与作者的多对多关系）

### 2.3 维度建模设计思考（核心）

#### 从原始数据到维度模型的思考过程

##### 第一步：理解原始数据的本质
拿到原始数据后，首先要回答三个关键问题：
1. **这些数据记录了什么业务活动？**（识别业务过程）
2. **业务关心什么指标？**（识别度量）
3. **从哪些角度分析这些指标？**（识别维度）

##### 第二步：事实表与维度表识别（两种方法）

**方法一：业务驱动识别法（理想情况）**
```
当你了解业务时，通过动词识别：
- "申请"专利 → fact_patent_application
- "投资"企业 → fact_investment_event  
- "发布"研报 → fact_research_report
- "获得"资助 → fact_policy_funding
```

**方法二：数据驱动识别法（实际情况）**

作为分析平台，往往先有数据后理解业务，需要从数据特征判断：

```
判断决策树：
1. 这张表的数据是否会持续增长？
   ├─ 是 → 可能是事实表
   │   └─ 每条记录是否有时间戳？
   │       ├─ 是 → 交易型事实表
   │       └─ 否 → 需要进一步分析
   └─ 否 → 可能是维度表
       └─ 是否是描述性的主数据？
           ├─ 是 → 维度表
           └─ 否 → 可能是配置表或映射表
```

**基于数据特征的判断矩阵：**

| 数据特征 | 事实表特征 | 维度表特征 |
|---------|-----------|-----------|
| **记录增长模式** | 持续增长，很少删除 | 缓慢增长，相对稳定 |
| **数据量级** | 百万到十亿级 | 千到百万级 |
| **主要内容** | 数值型度量（金额、数量） | 描述性文本（名称、类型） |
| **时间属性** | 必有事件时间 | 可选，用于历史追踪 |
| **更新频率** | 只插入，不更新 | 可能更新（SCD） |
| **记录代表** | 业务活动/事件 | 业务实体/对象 |
| **主键特征** | 通常是代理键或组合键 | 通常有业务主键 |

**实例：拿到一张陌生数据表**
```sql
-- 表：investment_data
-- 字段：id, date, company_name, investor_name, amount, round

数据样例：
1, 2024-01-15, XX科技, 红杉资本, 5000万, B轮
2, 2024-01-16, YY科技, 高瓴资本, 3000万, A轮
3, 2024-01-17, XX科技, IDG资本, 2000万, B轮

分析过程：
1. 有日期字段(date) ✓
2. 有数值度量(amount) ✓  
3. 记录持续增长 ✓
4. 每条代表一个事件 ✓
→ 判断：事实表

但注意到：
- company_name重复出现 → 应拆分为企业维度表
- investor_name重复出现 → 应拆分为投资机构维度表
- round是分类属性 → 可作为维度表或退化维度
```

**快速判断口诀：**
```
"会计数的是事实，用来描述的是维度"
"流水数据是事实，主数据是维度"
"每天都有新记录是事实，基本不变的是维度"
```

##### 第三步：从源表到维度模型的改造思路

**场景：接手已有的业务系统表**

当分析平台接入源系统数据时，通常面对的是OLTP设计的规范化表结构，需要改造成面向分析的维度模型：

```
源系统表结构示例（OLTP）：
├── t_investment（投资表）
│   ├── id, event_date, amount, status
├── t_investment_detail（投资明细）
│   ├── investment_id, investor_id, amount, type
├── t_company（企业表）
│   ├── id, name, industry, location
└── t_investor（投资方表）
    ├── id, name, type, capital

改造思路：
1. 识别核心业务表
   - t_investment有日期和金额 → 改造为事实表
   - t_investment_detail是明细 → 可能需要聚合或作为明细事实表

2. 识别描述性表
   - t_company、t_investor → 改造为维度表
   
3. 处理关联关系
   - 一对多：直接外键关联
   - 多对多：增加桥接表

改造结果：
├── fact_investment_event（事实表）
├── fact_investment_participation（明细事实表）
├── dim_company（企业维度）
├── dim_investor（投资方维度）
└── bridge_investment_investor（桥接表）
```

**常见源表模式的改造映射：**

| 源表模式 | 典型特征 | 改造方向 |
|---------|---------|---------|
| **主表+明细表** | 订单+订单明细 | 主表→汇总事实表<br>明细→明细事实表 |
| **流水记录表** | 日志、交易流水 | →事务事实表 |
| **状态记录表** | 余额、库存快照 | →周期快照事实表 |
| **基础数据表** | 产品、客户、员工 | →维度表 |
| **关系映射表** | 用户角色、产品分类 | →桥接表或层级维度 |
| **配置参数表** | 系统配置、枚举值 | →维度表或退化维度 |

**实战案例：专利系统表改造**
```sql
-- 源系统：多张规范化表
patent_basic (专利基本信息)
patent_applicant (申请人，1:N)  
patent_inventor (发明人，1:N)
patent_classification (分类，1:N)
patent_legal_event (法律事件，1:N)

-- 分析需求：
-- 1. 分析专利申请趋势
-- 2. 分析技术领域分布
-- 3. 追踪法律状态变化

-- 改造方案：
1. patent_basic + patent_legal_event 
   → fact_patent_lifecycle (生命周期事实表)
   
2. patent_applicant + patent_inventor
   → dim_patent_party (统一关系方维度)
   → fact_patent_party_association (关系事实表)
   
3. patent_classification
   → dim_classification (分类维度)
   → bridge_patent_classification (桥接表)
```

##### 第四步：确定事实表粒度

**粒度选择决策树：**
```
问题1：一条记录代表什么？
├── 单一事件 → 最细粒度
│   └── 例：一次专利申请、一笔投资
├── 多个相关事件 → 需要拆分
│   └── 例：一轮融资包含多个投资方
└── 周期性快照 → 特定时点状态
    └── 例：月末专利持有状态

问题2：是否需要拆分？
├── 存在1:N关系 → 拆分为主事实表+明细表
│   └── 例：投资事件 + 机构参与明细
└── 属性完全依赖主键 → 保持单表
```

**粒度设计原则：**
- **最细粒度原则**：尽可能保持最细粒度，聚合可以后续处理
- **一致性原则**：相同主题域内粒度保持一致
- **可加性原则**：度量值在选定粒度上必须可加

##### 第五步：维度识别与分类

**维度识别方法：5W1H分析法**
```
Who（谁）   → 主体维度：企业、机构、人员
What（什么） → 对象维度：产品、专利、政策
When（何时） → 时间维度：日期、会计期
Where（哪里）→ 地理维度：国家、省市、地区
Why（为何）  → 原因维度：类型、状态、原因
How（如何）  → 方式维度：渠道、方法、流程
```

**维度分类决策：**
```
判断流程：
1. 该属性是否描述"是什么"而非"有多少"？
   是 → 维度属性
   否 → 度量
   
2. 该维度是否被多个事实表共享？
   是 → 一致性维度（独立维度表）
   否 → 考虑退化维度
   
3. 该维度的基数（唯一值数量）如何？
   高基数(>10000) → 独立维度表
   中基数(100-10000) → 独立维度表或退化维度
   低基数(<100) → 退化维度

4. 该维度是否需要保留历史？
   是 → SCD Type-2维度表
   否 → SCD Type-1维度表
```

**实例：专利数据维度识别**
```
原始数据分析：
专利号、申请人、发明人、申请日期、技术领域、
法律状态、引用次数、权利要求数...

维度识别结果：
├── 独立维度表
│   ├── dim_patent（专利本身属性）
│   ├── dim_patent_party（申请人/发明人，高基数）
│   └── dim_classification（技术分类，层级结构）
├── 退化维度
│   └── legal_status（法律状态，低基数）
└── 度量
    ├── citation_count（引用次数）
    └── claim_count（权利要求数）
```

##### 第六步：复杂关系处理策略

**多对多关系处理：**
```
场景：一个研报有多个作者，一个作者写多个研报

方案选择：
1. 桥接表（推荐）
   bridge_report_researcher
   - 保持关系的完整性
   - 支持额外属性（如作者顺序）
   
2. 多值维度
   dim_report.author_list (JSON/ARRAY)
   - 查询简单但灵活性差
   - 适合关系简单且稳定的场景
```

**角色扮演处理：**
```
场景：投资机构在不同事件中角色不同（投资方/退出方）

方案：角色维度化
fact_investment_participation
├── sk_event_id（关联投资或退出事件）
├── sk_institution_id（机构）
├── role_type（投资方/退出方）
└── amount（参与金额）
```

**层级结构处理：**
```
场景：产业链6级分类体系

方案：宽表冗余
dim_industry_chain
├── level_1_code / level_1_name
├── level_2_code / level_2_name
├── ...
└── level_6_code / level_6_name

优点：查询性能好，路径清晰
缺点：更新复杂，存储冗余
```

##### 第七步：度量设计原则

**度量分类：**
```
可加度量（Additive）
├── 完全可加：金额、数量
└── 使用：可在所有维度上求和

半可加度量（Semi-Additive）
├── 示例：余额、库存
└── 使用：不能跨时间求和

不可加度量（Non-Additive）
├── 示例：比率、单价
└── 使用：需要重新计算，不能直接求和
```

**度量设计检查清单：**
- [ ] 度量是否具有明确的业务含义？
- [ ] 度量的单位是否统一？
- [ ] 是否需要存储原币和本币金额？
- [ ] 空值的业务含义是什么（0还是NULL）？
- [ ] 是否需要存储计算过程的中间值？

##### 第八步：设计验证与优化

**验证方法：查询模拟**
```sql
-- 模拟业务查询，验证模型设计
-- 查询：2024年各投资机构的投资金额排名

SELECT 
    i.institution_name,
    SUM(f.investment_amount) as total_amount,
    COUNT(DISTINCT f.pk_investment_event_id) as event_count
FROM fact_investment_event f
JOIN dim_investment_institution i 
    ON f.sk_institution_id = i.sk_institution_id  -- 错误！
-- 发现问题：事实表无法直接关联机构

```

**优化决策：**
```
问题：查询需要多次JOIN影响性能
解决方案评估：
1. 冗余常用维度属性到事实表 ✓
2. 创建宽表（汇总层）✓
3. 物化视图 ✓
4. 保持规范化设计 ✗（查询复杂）
```

### 2.4 逻辑模型转化

#### 第一步：表类型设计模式

##### 事实表设计模式
```sql
-- 事务型事实表示例（投融资事件）
CREATE TABLE fact_investment_event (
    pk_investment_event_id STRING,      -- 主键（唯一标识）
    sk_investment_event_id BIGINT,      -- 代理键（关联维度）
    sk_date BIGINT,                     -- 时间维度外键
    sk_enterprise_id BIGINT,            -- 企业维度外键
    sk_location BIGINT,                 -- 地区维度外键
    sk_round BIGINT,                    -- 轮次维度外键
    sk_currency BIGINT,                 -- 币种维度外键
    investment_amount DECIMAL(18,2),    -- 度量：投资金额
    investment_amount_foreign DECIMAL(18,2), -- 度量：外币金额
    -- 退化维度
    disclosure_status STRING,            -- 披露状态
    dt STRING                            -- 分区字段
);

-- 周期快照型事实表示例（专利生命周期）
CREATE TABLE fact_patent_lifecycle_snapshot (
    pk_patent_lifecycle_snapshot_id STRING,
    sk_patent_id BIGINT,
    sk_application_date BIGINT,         -- 申请日期
    sk_publication_date BIGINT,         -- 公开日期
    sk_approval_date BIGINT,            -- 授权日期
    cited_by_patent_number BIGINT,      -- 被引用次数（累积度量）
    patent_approval_number BIGINT,      -- 授权数量（累积度量）
    dt STRING
);
```

##### 维度表设计模式
```sql
-- SCD Type-1 维度表（覆盖更新）
CREATE TABLE dim_investment_institution (
    bk_investment_institution_id STRING,  -- 业务键
    sk_investment_institution_id BIGINT,  -- 代理键
    institution_name STRING,
    institution_type STRING,
    capital_background STRING,
    sk_location BIGINT,                   -- 外键关联地区维度
    sk_enterprise_id BIGINT,              -- 外键关联企业维度
    dt STRING
);

-- SCD Type-2 维度表（保留历史）
CREATE TABLE dim_researcher (
    bk_researcher_id STRING,
    sk_researcher_id BIGINT,
    sk_institution_id BIGINT,
    researcher_name STRING,
    -- SCD控制字段
    scd_start_date DATE,
    scd_end_date DATE,
    is_current BOOLEAN,
    dt STRING
);
```

##### 桥接表设计模式
```sql
-- 解决多对多关系
CREATE TABLE bridge_report_researcher (
    pk_report_researcher_id STRING,      -- 复合主键
    sk_report_id BIGINT,                 -- 外键：研报
    sk_researcher_id BIGINT,             -- 外键：研究员
    author_order INT,                    -- 作者顺序
    dt STRING
);
```

#### 第二步：代理键生成策略

统一采用64位xxhash算法生成代理键：
```sql
-- 代理键生成规则
sk_patent_id = xxhash(public_announcement_number)
sk_enterprise_id = xxhash(enterprise_business_id)
sk_investment_event_id = xxhash(logic_id)

-- 关联不上时的处理
sk_enterprise_id = CASE 
    WHEN enterprise_id IS NULL THEN -1
    WHEN dim.sk_enterprise_id IS NULL THEN xxhash(enterprise_id) * -1
    ELSE dim.sk_enterprise_id
END
```

### 2.7 数据质量保障

#### 第一步：主键完整性检查

- 维度表主键：`bk_` 前缀，业务键唯一
- 代理键：`sk_` 前缀，非空约束

## 三、设计模式最佳实践

### 3.1 复杂业务场景处理

#### 场景一：多角色参与（投融资）
```
设计方案：
fact_investment_event（事实表）
  ↓
dim_investment_participation（参与行为维度）
  ↓
dim_investment_institution（机构维度）

通过参与行为维度表记录机构在事件中的角色（领投/跟投/退出方）
```

#### 场景二：多语种支持（专利）
```
设计方案：
dim_patent（专利主维度，含主要语种）
  ↓
og_patent_text（支架表，存储多语种文本）

支架表按语种存储标题和摘要，通过is_origin标识原始语种
```

#### 场景三：层级结构（产业链）
```
设计方案：
dim_industry_chain_graph_information
├── node_code_lv1 / node_name_lv1  -- 一级节点
├── node_code_lv2 / node_name_lv2  -- 二级节点
├── ...
└── node_code_lv6 / node_name_lv6  -- 六级节点

采用宽表形式存储完整层级路径，支持逐级钻取
```

### 3.2 性能优化策略

#### 策略一：合理使用退化维度
将低基数、不常变化的维度属性直接存储在事实表中：
- disclosure_status（披露状态）
- exit_method（退出方式）
- role_type（角色类型）

#### 策略二：预聚合设计
对高频查询场景，在DWT层预先计算聚合指标：
- cited_by_patent_number（专利被引用次数）
- patent_approval_number（专利授权数量）
- funding_amount（扶持资金总额）

#### 策略三：索引优化
```sql
-- 在高频关联字段上创建索引
CREATE INDEX idx_fact_investment_sk_date ON fact_investment_event(sk_date);
CREATE INDEX idx_fact_investment_sk_enterprise ON fact_investment_event(sk_enterprise_id);
```
